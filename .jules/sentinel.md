## 2024-05-24 - [CRITICAL] RefCell Borrow Panics & Aliased Account Data Loss
**Vulnerability:** In solana programs, directly utilizing `.borrow_mut()` on account lamports without `try_borrow_mut_lamports` can lead to program panics if double-borrowing occurs, rather than securely bubbling up an error. Additionally, doing unsafe arithmetic operations (`+=`, `-=`) on lamports or using them within assignments across multiple aliased accounts causes functional regressions, like aliased accounts overwriting each other's updates or running into numerical overflows.
**Learning:** Due to Rust evaluating the left-hand operand of an assignment first, attempting to calculate the right-hand side simultaneously can cause runtime `RefCell` borrow panics if the calculation also reads from the same account. It is crucial to read the account's lamports, compute the new lamports value safely with `.checked_add`/`.checked_sub`, and finally assign the new lamports.
**Prevention:** Always use safe methods `.try_borrow_mut_lamports()?` and `.try_borrow_mut_data()?`. Employ an alternating read-compute-write sequence for updating account lamports (i.e. calculate the new value first entirely in a separate line and assign it to the mutable borrow afterwards). Convert operations failing this to `MplCoreError::NumericalOverflowError` using `.ok_or`.
