## 2025-02-14 - Fix panic during runtime account modifications
**Vulnerability:** In `programs/mpl-core/src/utils/account.rs`, there were modifications made directly to `RefCell` structures during lamport updates via `.lamports.borrow_mut()`, and there was an unwrapped `Key::Uninitialized.to_u8().unwrap()` which could panic. In addition to this, assigning to the result of `try_borrow_mut_lamports()?` while the RHS uses `.checked_add` and reads the lamports simultaneously can cause double borrow panics.
**Learning:** In Solana, directly calling `.borrow_mut()` on `AccountInfo` fields like `.lamports` or `.data` can lead to program panics if the same value is accessed elsewhere concurrently in the same context. Further, `.unwrap()` usage on simple type conversions from `enum` types creates an unnecessary attack surface. Additionally, assigning to a mutable reference returned by `.try_borrow_mut_lamports()?` in the LHS *before* the RHS evaluates it can trigger runtime double borrow panics in Solana's `AccountInfo`.
**Prevention:** Always use safe accessors like `.try_borrow_mut_lamports()?` and `.try_borrow_mut_data()?`. Avoid `.unwrap()` and `.expect()` everywhere, replacing with safe unwrapping via `.ok_or()` mapped to program errors. When modifying lamports, explicitly compute the updated values using `.lamports()` and safe arithmetic before assigning them to the mutated field.
