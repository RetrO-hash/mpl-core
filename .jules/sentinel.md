## 2024-05-18 - Unsafe Arithmetic Leading to Potential Panics

**Vulnerability:** The Solana program `mpl-core` used `+=` and `-=` directly on lamports accessed via `try_borrow_mut_lamports()`, without using `checked_add` or `checked_sub`. Also, `dest_starting_lamports` calculated before `amount_to_return` is mutated and assigned instead of properly assigning to `try_borrow_mut_lamports()?`. Furthermore, it used `.borrow_mut()` to access RefCell wrapped values directly instead of using `.try_borrow_mut...()`.

**Learning:** Direct arithmetic operators (`+=`, `-=`) on `try_borrow_mut_lamports()` dereferenced values can lead to integer overflow/underflow, causing the Solana program to panic unconditionally. Unhandled overflows/underflows in token/lamport balances are a critical vulnerability in smart contracts. Similarly, using `.borrow_mut()` directly on `RefCell` wrapper (for data and lamports) can cause an immediate panic when the struct is already borrowed. We must always rely on `.try_borrow_mut_lamports()?` and `.try_borrow_mut_data()?`. Finally, when doing variable updates on lamports with `.checked_add` or `.checked_sub`, the value should be computed first from current lamports and then properly assigned with `=` to the `AccountInfo` lamports.

**Prevention:** Always use safe math functions (`checked_add`, `checked_sub`) and handle the `None` case gracefully (e.g., mapping to a `NumericalOverflowError`) to ensure deterministic program failure rather than uncontrolled panics. Use the `try_borrow_mut` variants on `AccountInfo` fields. Ensure that the computed balance is safely stored back using `=` assignment.
