## 2026-04-07 - Unsafe Lamport Modification & RefCell Double Borrow
**Vulnerability:** Solana smart contracts performing `**account_info.lamports.borrow_mut() = account_info.lamports().checked_add(...)` trigger runtime ungraceful panics due to Rust evaluating the mutable `RefCell` borrow (`borrow_mut()`) on the left side of the assignment before the read (`lamports()`) on the right side. Similarly, using the `+=` and `-=` operators directly on `try_borrow_mut_lamports()?` poses numeric overflow panic risks and bypasses the explicit `ok_or` error handling.
**Learning:** In Solana, direct access to `AccountInfo::lamports` or `AccountInfo::data` via `.borrow_mut()` is inherently unsafe because it will cause the program to crash ungracefully (double borrow panic) rather than return a predictable runtime error to the client. This becomes a vector for DoS if an attacker can force simultaneous mutable and immutable borrows.
**Prevention:** Always use `.try_borrow_mut_lamports()?` and `.try_borrow_mut_data()?`. Additionally, compute the entire new lamport value using explicit `.checked_add()` / `.checked_sub()` in a separate let-bound variable *before* invoking the mutable borrow and assignment to guarantee borrowing rules aren't broken simultaneously.
