## 2024-06-15 - Unsafe Lamport Operations and RefCell Panics

**Vulnerability:** The codebase was directly modifying account lamports using `**account_info.lamports.borrow_mut() = ...` and using potentially unsafe operators `+=` and `-=` without overflow checks. Modifying `.borrow_mut()` directly without `.try_borrow_mut_lamports()?` can cause the program to ungracefully panic if there's a double borrow. In addition, right-side evaluation inside the assignment statement when modifying lamports can cause double-borrow panics since rust evaluates left-side first, borrowing the account, then it tries to borrow again for the right side lamports read.

**Learning:** Solana's `AccountInfo` fields are wrapped in `Rc<RefCell<...>>`. Using `.borrow_mut()` causes an immediate program panic if the inner value is already borrowed, rather than a graceful program failure that clients can handle. Furthermore, modifying lamports directly using standard arithmetic operators `+=` and `-=` is susceptible to underflow/overflow panics if logic is incorrect or unexpected state occurs.

**Prevention:** Always use `.try_borrow_mut_lamports()?` and `.try_borrow_mut_data()?` instead of `.borrow_mut()` for safety to return a clean error if an issue occurs. Always use `.checked_add()` and `.checked_sub()` for any operations on lamports instead of raw arithmetic operators, failing the transaction with a custom error `MplCoreError::NumericalOverflowError` on overflow. Calculate the new value *before* assigning it to the mutably borrowed lamports to ensure the account is not double-borrowed during the assignment line.
